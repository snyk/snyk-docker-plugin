# Plan: Rust (Cargo) application-dependency scanning

Ticket: poc-pg0 — add Rust support in snyk-docker-plugin.

## Decision on the blocker noted by Triage

Triage paused on "does a Rust/Cargo lockfile parser library exist?". The
human has since directed: **do not take on an external Rust-lockfile-parser
dependency — write the parser ourselves, in this repo.** This unblocks
planning; no external package (npm or otherwise) is required for parsing
`Cargo.lock`. We follow the precedent already in this codebase of
`lib/analyzer/applications/dotnet.ts`, which hand-parses `*.deps.json`
and builds the graph directly with `@snyk/dep-graph`'s `DepGraphBuilder`,
rather than wrapping a third-party lockfile-parser library the way
`php.ts`/`poetry.ts` do. No new runtime dependency is added.

`Cargo.lock` is machine-generated by `cargo` and has a small, very regular
structure (a `version` key plus repeated `[[package]]` tables with a fixed,
known set of scalar/array fields). We do not need — and should not build —
a general-purpose TOML parser; a parser purpose-built for this shape is
enough, is easy to review, and avoids an external attack surface. This
should be explicitly documented in the code as a deliberate scope
limitation (not a general TOML parser).

## Scope

In scope (this repo only, `snyk/snyk-docker-plugin`):
1. Detect `Cargo.lock` (and `Cargo.toml`, for completeness of the file-pair
   pattern used elsewhere, though not required for graph construction) inside
   scanned image layers.
2. Parse `Cargo.lock` and build a `@snyk/dep-graph` `DepGraph` for the
   `cargo` package manager.
3. Emit existing fact types only (`depGraph`, `testedFiles`) — no new
   `FactType` is introduced, so no downstream-consumer contract change is
   needed in `snyk/cli`, `snyk/kubernetes-monitor`,
   `snyk/container-image-collector`, or `snyk/docker-registry-agent`. (This
   was flagged by Triage as a concern; it's resolved by reusing existing
   fact types, matching Triage's own finding that "existing FactTypes are
   sufficient".)
4. Unit tests (Jest, `.spec.ts`) covering the new parser/graph-builder with
   fixture `Cargo.lock` files.
5. Best-effort system test with a real container image containing
   `Cargo.lock`, following the `php`/`poetry` system-test pattern — see
   "System test" section below for the fallback if a Docker daemon isn't
   available to the Builder.

Out of scope (do not do in this ticket — flag separately if needed):
- Any change to `PluginResponse`/`ScanResult`/`Fact`/`FactType` shapes.
- Binary-level Rust analysis (e.g. parsing compiled Rust binaries for
  embedded crate/version info, analogous to `lib/go-parser`). Only
  manifest/lockfile-based scanning, matching the ticket's stated scope
  ("Cargo.toml/Cargo.lock parsing (application-level dependencies)").
- Dev-dependency inclusion — mirror existing ecosystems (php, poetry) which
  default `shouldIncludeDevDependencies = false`. Cargo.lock v3+ does not
  cleanly separate dev vs normal deps per-package anyway (that distinction
  lives in `Cargo.toml`, not the lock file), so this is moot for lockfile-only
  parsing — note this explicitly in code comments.
- Workspace edge cases beyond a simple "synthesize a virtual root" fallback
  (see below) — don't over-engineer multi-crate workspace member targeting.

## Files to add / change

### 1. `lib/inputs/rust/static.ts` (new)
Mirror `lib/inputs/php/static.ts`. An `ExtractAction` named
`getRustAppFileContentAction` (actionName: `"rust-app-files"`) whose
`filePathMatches` matches basenames `Cargo.toml` and `Cargo.lock`
(plus their `.wh.`-prefixed deleted-file variants, matching the php
pattern), and `callback: streamToString`.

### 2. `lib/analyzer/applications/rust.ts` (new)
Self-contained, modeled on `lib/analyzer/applications/dotnet.ts`:

- `parseCargoLock(content: string): CargoLockPackage[]` — the purpose-built
  parser. Splits the file into `[[package]]` blocks, and for each block
  extracts:
  - `name` (required, quoted string)
  - `version` (required, quoted string)
  - `source` (optional, quoted string) — **presence/absence of this field is
    the signal for "local/workspace package" vs "external registry/git
    dependency"**: cargo omits `source` only for the workspace's own
    member crates.
  - `dependencies` (optional array of quoted strings, each either `"name"`
    or `"name version"` — the latter form is used only when the lock file
    contains multiple versions of the same crate name).
  Malformed/unrecognized blocks are skipped defensively rather than
  throwing, consistent with the "don't fail the whole scan" convention used
  by `php.ts`. Add a code comment stating this is intentionally not a
  general TOML parser and why.

- `buildDepGraphFromCargoLock(lockContent, lockFilePath): DepGraph | null`:
  - Build a lookup by `name` and by `"name@version"`.
  - Determine root package(s): all packages with no `source`.
    - Exactly one → use it as the graph's root pkg (name/version).
    - Zero → return `null` (log via `debug`, skip the file — this would be
      an unusual/incomplete lock file).
    - More than one (a Cargo workspace) → synthesize a virtual root pkg
      (`name` derived from the lock file's directory basename, `version:
      "0.0.0"`) that directly depends on each local member package. Add a
      comment explaining this is a simplification.
  - Walk `dependencies` recursively via `DepGraphBuilder.addPkgNode` /
    `connectDep`, resolving each dependency string to a concrete package via
    the lookup (prefer exact `"name@version"` match when a version is given,
    else the sole entry for `name`; if ambiguous/unresolvable, skip that edge
    and `debug`-log it rather than throwing).
  - Use `eventLoopSpinner` the same way `dotnet.ts` does for large graphs.
  - pkgManager name: `"cargo"`.

- `rustFilesToScannedProjects(filePathToContent: FilePathToContent):
  Promise<AppDepsScanResultWithoutTarget[]>` — for every `Cargo.lock` path
  found (ignore standalone `Cargo.toml` entries with no adjacent lock file;
  a manifest with no lock file gives us nothing new to resolve versions
  from), call `buildDepGraphFromCargoLock`, and on success push a
  `depGraphFact` + `testedFilesFact` (`data: [path.basename(lockPath)]`)
  scan result with `identity: { type: "cargo", targetFile: lockPath }`.
  Wrap per-file parsing in try/catch + `debug` log, exactly like
  `dotnetFilesToScannedProjects`, so one bad lock file doesn't abort the scan.

### 3. `lib/analyzer/applications/index.ts`
Add `import { rustFilesToScannedProjects } from "./rust";` and re-export it,
alongside the existing ecosystem exports.

### 4. `lib/analyzer/static-analyzer.ts`
- Import `getRustAppFileContentAction` from `../inputs/rust/static`.
- Import `rustFilesToScannedProjects` from `./applications`.
- Add `getRustAppFileContentAction` to the `appScan` block's
  `staticAnalysisActions` push (alongside `getPhpAppFileContentAction` etc).
- Add a `phaseStart`/`rustDependenciesScanResults` block (mirroring the
  php/dotnet blocks) with a `timings.rustAnalysisMs` entry.
- Push `...rustDependenciesScanResults` into
  `applicationDependenciesScanResults`.

No changes needed to `lib/index.ts`, `lib/types.ts`, or `lib/facts.ts` —
no new public export or FactType is introduced.

### 5. `package.json`
No new dependency required (see "Decision on the blocker" above). If, once
implementing, a genuine need for even minimal help (e.g. nothing beyond
what's already used elsewhere) arises, that's a signal scope has grown
beyond this plan — raise it rather than silently adding a dependency.

## Tests

### Unit tests (required)
`test/lib/analyzer/rust.spec.ts`, modeled directly on
`test/lib/analyzer/dotnet.spec.ts`, using fixtures under
`test/fixtures/rust/`:

- `Simple.Cargo.lock` — one root crate with 1-2 direct external
  dependencies, no transitive deps. Assert: scan result count, `identity.type
  === "cargo"`, `identity.targetFile`, root pkg name/version, direct deps
  present in `depGraph.getPkgs()`.
- `WithTransitive.Cargo.lock` — root crate → dep → transitive dep. Assert
  transitive dep appears and is connected (use `depGraph.getDepPkgs`/
  equivalent, matching how `dotnet.spec.ts` asserts transitivity).
- `DuplicateVersions.Cargo.lock` — a lock file where a crate name appears
  twice at different versions and a dependency entry disambiguates with
  `"name version"` — assert the correct version is picked.
- `Workspace.Cargo.lock` — multiple packages with no `source` (simulating a
  workspace) — assert the synthetic root is created and depends on each
  member.
- `Malformed.Cargo.lock` (e.g. no `[[package]]` blocks, or all packages
  missing `version`) — assert `rustFilesToScannedProjects` returns `[]`
  rather than throwing.

Run with `npm run test:unit` (fast, no Docker needed) — this is the
Builder's primary inner loop and must pass before moving on.

### System test (best effort)
Add `test/system/application-scans/rust.spec.ts` mirroring
`php.spec.ts`/`poetry.spec.ts`, plus a fixture image
`test/fixtures/docker-archives/docker-save/rust.tar` containing a
`Cargo.toml` + `Cargo.lock` pair (a minimal `FROM scratch` image with just
those two files `COPY`'d in is sufficient — no actual Rust toolchain needs
to run inside the image; we're testing file discovery + parsing, not
compilation).

This step needs a running Docker daemon (`docker build` + `docker save`) to
produce the `.tar` fixture, per `AGENTS.md`'s testing rules. If the Builder's
environment doesn't have Docker available: **say so explicitly in the
ticket notes, ship the unit tests as the primary verification, and leave
the system test + fixture as a follow-up** rather than skipping it silently
or faking it. Do not hand-craft a fake docker-archive tar by hand if a real
`docker build`/`docker save` isn't available — that risks a fixture that
doesn't match what the real extractor expects.

## Definition of done
- `npm run build`, `npm run lint`, `npm run test:unit` all pass.
- `npm run test:system` passes if Docker is available; otherwise explicitly
  noted as not run, with the new system test + fixture committed anyway (it
  will run in CI, which has Docker).
- No changes to public `PluginResponse`/`ScanResult`/`Fact`/`FactType`
  shapes — confirmed by not touching `lib/facts.ts`/`lib/types.ts`.
- Conventional commit(s), e.g. `feat: add Rust (Cargo.lock) application dependency scanning`.

## Sizing
This is a single, cohesive, appropriately-bounded unit of work for one
Builder — one new ecosystem following an existing, well-trodden template
(`dotnet.ts` for the "self-built parser, no external lib" shape). Not
splitting into child tickets.
